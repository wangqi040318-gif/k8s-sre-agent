## 问题

Kubernetes 告警进群后，值班的人要在 Pod 状态、Events、日志和 Runbook 之间来回翻。镜像拉不下来、内存被杀、进程崩溃之外，日常更多的是 Pod 排不上、配置没挂上、探针不过、Service 没有后端。证据分散，处置命令又带写操作。把「查完就自动改集群」交给模型，误改的代价大于少看一份报告。

本作品处理告警分诊的前几分钟：把取证、Runbook 检索和处置建议收成一份可复核的报告，写操作留在人工确认之后。

## 做法

流水线固定为取证、检索、诊断，优先用 LangGraph；导入失败时按同一顺序走 Python 状态机。诊断图里没有执行节点。

1. **取证。** 读 Pod、Events、日志和 describe。默认 `MOCK=1`，用仓库里的固定证据，没有集群也能复现。`MOCK=0` 且配置了 kubeconfig 时改读真实 API。
2. **检索。** 用证据拼查询，在本地 TF-IDF 索引里取 Runbook。索引来自 `runbooks/*.md`，不依赖向量数据库和外网。
3. **诊断。** 配置了兼容 OpenAI 的 Key 时，模型按 `prompts/` 写中文报告。没有 Key 时用规则模板，命令行和测试不依赖外部模型。
4. **确认后执行。** 提案来自动作目录，不采用模型随手写的命令。CLI 的 `--confirm` 只接受大写 `YES`；交互终端和 Streamlit 只接受原样 `CONFIRM`。未确认就拒绝并写审计日志。Mock 下确认后只更新进程内状态。

## 技术栈与演示

Python 3、LangGraph、OpenAI 兼容接口（通义 / DeepSeek / OpenAI）、本地 TF-IDF、kubernetes 客户端、Streamlit、pytest。环境模板是 `.env.example`。

| 场景 | 证据要点 | 确认后的演示动作 |
|---|---|---|
| ImagePullBackOff | 镜像 Tag 不存在，Events 为 Failed / BackOff | `fix-image`：改为 `nginx:1.27` |
| OOMKilled | memory limit `64Mi`，exitCode 137 | `bump-memory`：调到 `256Mi` |
| CrashLoopBackOff | 缺配置导致退出，重启次数升高 | `fix-command`：改为健康休眠并移除探针 |
| Pending / 无法调度 | request 为 8 CPU / 16Gi，且亲和性指向不存在的节点 | `relax-scheduling`：降到可调度值并去掉错误亲和性 |
| ConfigMap 挂载失败 | `app-config` 不存在，CreateContainerConfigError 与 FailedMount | `create-config`：只补这个非敏感 ConfigMap |
| 探针未就绪 | 进程监听 80，探针访问 8080 `/healthz` | `fix-probe`：改 path `/`、port `80`，不删探针 |
| Service 无 Endpoints | Pod 标签 `app=demo`，Service 仍选 `app=frontend` | `fix-selector`：只改 selector |

上调内存和休眠命令只用于打断演示中的故障循环，不能代替泄漏排查或补齐生产配置。调度、探针和选择器的演示动作同样只覆盖证据里的那一处，不改节点，不放宽 NetworkPolicy，不写 Secret。

## 岗位对应

作品对应云原生 / SRE 值班里的四件事：只读取证、按 Runbook 缩小范围、把变更写成可审计的提案、变更默认关闭。它说明作者能把大模型放进有工具、有知识库、有人工闸门的运维流程。结构、复现和案例见 `docs/技术文档.md`。
